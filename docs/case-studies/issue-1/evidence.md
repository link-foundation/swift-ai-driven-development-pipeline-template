# Collected evidence

| Source | Observation |
| --- | --- |
| [Issue #1](https://github.com/link-foundation/swift-ai-driven-development-pipeline-template/issues/1) | Build a full Swift equivalent of Hive Mind's CI/CD guide, report adoption tasks to Hive Mind and UI, and keep the research, requirements and solution plans together in this PR. Issue comments and sub-issue lists were empty at intake. |
| [PR #2 at intake](https://github.com/link-foundation/swift-ai-driven-development-pipeline-template/pull/2/commits/83b0b6b9bef2a18a29a80196d75341e18fa0ba64) | The initial draft added a placeholder. Conversation, inline review and review lists were empty, and the branch had no Actions runs. |
| [Baseline](https://github.com/link-foundation/swift-ai-driven-development-pipeline-template/tree/1bc65333e14ff33d199cd7064105df04ace032c6) | The default branch provided a README, license and Swift/Xcode ignore file. It had no package manifest, workflows, release state or test suite. The repository had no main-branch rulesets at intake. |
| [Hive Mind guide revision](https://github.com/link-assistant/hive-mind/blob/0f07c025bdf67f7391c7d5c47baf9ffca6fed1c9/docs/CI-CD-BEST-PRACTICES.md) | Seventeen principles cover filtered CI, local gates, release recovery, OCI publishing and the difference between a failed check and unavailable infrastructure. |
| [Hive Mind C/C++ integration](https://github.com/link-assistant/hive-mind/pull/2574) | Template adoption updated language detection, all localized docs, and the inventory tests together. This gives the Swift adoption report a concrete precedent. |
| [UI Swift workflow](https://github.com/link-foundation/ui/blob/b4888152ba357c1418c9628dc4a998c1e52d5cfa/.github/workflows/swift.yml) | UI already had four Swift jobs. It builds the vendored parser and the root SwiftPM manifest on Linux and macOS, and captures SwiftUI screenshots on macOS. The template must preserve these project-specific checks. |
| [UI package manifest](https://github.com/link-foundation/ui/blob/b4888152ba357c1418c9628dc4a998c1e52d5cfa/Package.swift) | SwiftPM consumers depend on the repository URL. The manifest selects platform-appropriate products and points at several source directories. This favors a configurable caller over moving the manifest for the pilot. |
| [SwiftPM dependencies](https://docs.swift.org/swiftpm/documentation/packagemanagerdocs/addingdependencies/) and [lockfile guidance](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/PackageManagerDocs/Documentation.docc/ContinuousIntegration.md) | Git tags drive SCM dependency versions. Committing the resolution captures the exact transitive graph that CI should test and audit. |
| [OSV-Scanner Swift support](https://github.com/google/osv-scanner/releases/tag/v2.4.0) and [Dependabot ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference) | OSV-Scanner enables the SwiftURL `Package.resolved` extractor starting in v2.4. Dependabot has a Swift updater, which becomes useful when the starter has a Git dependency. |
| [GitHub merge queues](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-organization/configuring-pull-request-merges/managing-a-merge-queue) and [concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) | A merge queue requires the `merge_group` trigger. A shared writer group prevents overlapping writers, but each workflow still begins at its triggering SHA and must account for intervening commits. |
| [Official Swift Docker images](https://github.com/docker-library/official-images/blob/master/library/swift) and [Swift on GitHub Actions](https://docs.github.com/en/actions/tutorials/build-and-test-code/swift) | Native Linux arm64 and amd64 builds can share a Dockerfile. Linux and macOS Actions runners support SwiftPM and provide complementary platform coverage. |
